# Phase 7: Output Generators - Research

**Researched:** 2026-01-23
**Domain:** Build file generation (Ninja), IDE integration (compile_commands.json), shared library building
**Confidence:** HIGH

## Summary

This phase generates Ninja build files and compile_commands.json for external tool integration. The research focused on three main areas: (1) Ninja build file format and generation patterns, (2) JSON compilation database specification for IDE integration, and (3) shared library building with proper PIC handling and platform-specific concerns.

**Key findings:**
- Ninja is explicitly designed as a low-level build executor with input files generated by higher-level tools—manual writing is an anti-pattern
- The compile_commands.json format is simple but has critical subtleties for IDE compatibility (particularly header file handling and include path resolution)
- Shared library building requires platform-specific handling: `-fPIC` on Linux, `install_name` with `@rpath` on macOS, and careful symbol visibility management

**Primary recommendation:** Use structured Go code generation (not templates) for Ninja files to ensure correctness, leverage the github.com/Duncaen/go-ninja library for AST-based generation, and generate compile_commands.json directly as JSON with proper escaping for all platforms.

### Pattern 1: Structured Generation (Not Templates)

**What:** Build Ninja files and compile_commands.json using Go structs that serialize to the target format, rather than string templates.

**When to use:** Always for this phase—eliminates entire classes of bugs (escaping, syntax errors, missing fields).

**Example (Ninja):**
```go
// Source: github.com/Duncaen/go-ninja documentation
import "github.com/Duncaen/go-ninja"

func generateNinja(cfg *config.Config, variant string) (*ninja.File, error) {
    file := ninja.File{}

    // Variables
    file = append(file, ninja.Var{Key: "builddir", Val: ".ninja_build"})
    file = append(file, ninja.Var{Key: "cc", Val: "clang"})

    // Rule for compilation
    file = append(file, ninja.Rule{
        Name:    "cc",
        Command: "$cc $cflags -MD -MF $out.d -c $in -o $out",
        Depfile: "$out.d",
        Deps:    ninja.DepsGCC,
        Description: "CC $out",
    })

    // Build statement
    file = append(file, ninja.Build{
        Rule: "cc",
        In:   []string{"src/main.cpp"},
        Out:  []string{"build/debug/obj/main.o"},
    })

    return &file, nil
}
```

**Example (compile_commands.json):**
```go
// Source: Clang JSON Compilation Database spec
type CompileCommand struct {
    Directory string   `json:"directory"`
    File      string   `json:"file"`
    Arguments []string `json:"arguments,omitempty"`
    Command   string   `json:"command,omitempty"`
    Output    string   `json:"output,omitempty"`
}

func generateCompDB(cfg *config.Config, variant string) ([]CompileCommand, error) {
    commands := []CompileCommand{}

    for _, target := range cfg.Targets {
        for _, src := range target.Sources {
            cmd := CompileCommand{
                Directory: absPath(cfg.RootDir),
                File:      absPath(filepath.Join(cfg.RootDir, src)),
                Arguments: buildCompilerArgs(cfg, target, src),
                Output:    objectPath(cfg.BuildDir, variant, target.Name, src),
            }
            commands = append(commands, cmd)
        }
    }

    return commands, nil
}
```

### Pattern 2: Multi-Config Ninja via Phony Targets

**What:** Single build.ninja file with variant-specific targets accessed via phony aliases (`ninja debug`, `ninja release`).

**When to use:** When user wants all variants available from one file (per Phase 7 context decisions).

**Structure:**
```ninja
# Top-level variables
builddir = .ninja_build

# Shared rules (one copy)
rule cc
  command = $cc $cflags -MD -MF $out.d -c $in -o $out
  depfile = $out.d
  deps = gcc
  description = CC $out

# Variant-specific builds
build build/debug/obj/main.o: cc src/main.cpp
  cflags = -g -O0

build build/release/obj/main.o: cc src/main.cpp
  cflags = -O2 -DNDEBUG

# Phony targets for user convenience
build debug: phony build/debug/bin/myapp
build release: phony build/release/bin/myapp

# Default target
default debug
```

### Pattern 3: Dependency Tracking with depfile

**What:** Use compiler-generated dependency files (`.d` files) for automatic header dependency tracking.

**When to use:** Always for C/C++ compilation—manual dependency specification doesn't scale.

**How it works:**
1. Compiler generates Makefile-format dependency file with `-MD -MF $out.d`
2. Ninja reads depfile after build, updates dependency graph
3. Ninja deletes `.d` file (temporary artifact)

**Ninja rule configuration:**
```go
rule := ninja.Rule{
    Name:    "cc",
    Command: "$cc -MD -MF $out.d $cflags -c $in -o $out",
    Depfile: "$out.d",
    Deps:    ninja.DepsGCC,  // or ninja.DepsMSVC for MSVC
}
```

**CRITICAL:** Always set both `Depfile` and `Deps` fields. Omitting `Deps` means Ninja won't process the file.

### Pattern 4: Response Files for Long Command Lines

**What:** Write long argument lists to temporary files, pass `@file.rsp` to compiler.

**When to use:** Windows (8191 byte command limit) or projects with many source files.

**Ninja configuration:**
```go
rule := ninja.Rule{
    Name:        "link",
    Command:     "$ld @$out.rsp -o $out",
    Rspfile:     "$out.rsp",
    RspfileContent: "$in $libs",
    Description: "LINK $out",
}
```

**Platform decision:** Generate response files for link steps on all platforms (simplifies cross-platform builds), use direct arguments for compilation (shorter, better error messages).

### Anti-Patterns to Avoid

- **Using absolute paths in Ninja files:** Breaks portability and can hit command-line length limits. Always use relative paths from project root or `builddir`.
- **Hand-writing Ninja files:** Error-prone (escaping `$`, `:`, spaces), no validation. Use structured generation.
- **Omitting `description` in rules:** Users see raw command lines instead of clean progress output (`CC main.o` vs `clang -g -O0 -std=c++20 -Iinclude...`).
- **Not using depfiles:** Leads to incorrect incremental builds (missing header changes) or massive over-rebuilding (conservative dependencies).
- **Generating separate .ninja files per config:** User requested single file with phony targets. Separate files (CMake Ninja Multi-Config pattern) would violate requirements.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Ninja syntax generation | String concatenation with escaping | github.com/Duncaen/go-ninja | Handles escaping (`$`, `:`, spaces, newlines), version compatibility, proper structure |
| Compiler flag ordering | Manual list construction | Reuse internal/build.Compiler logic | Flag order matters (include paths, defines), already tested |
| Path normalization | String manipulation | filepath.Clean, filepath.Rel | Handles `.`, `..`, mixed separators, edge cases |
| JSON escaping | Manual backslash insertion | encoding/json.Marshal | Unicode, control characters, quotes, all edge cases |
| Header dependency scanning | Parse #include directives | Compiler's `-MD` flag | Handles conditional includes, macro expansion, compiler-specific paths |

**Key insight:** Build file generation is **translation**, not invention. The build package already knows correct command construction—generators should reuse that logic rather than reimplementing it.

## Common Pitfalls

### Pitfall 1: compile_commands.json Missing Dependency Headers

**What goes wrong:** IDE can't navigate into dependency headers, shows "file not found" errors for vendored/external includes.

**Why it happens:** compile_commands.json only includes commands for files that are **compiled**, not headers. However, IDEs need compilation commands for headers to understand include paths.

**How to avoid:**
1. Use `arguments` field (not `command`) so IDE tools parse correctly
2. Include compilation commands for **all dependency sources** in the selected variant
3. For header-only libraries, create a synthetic compile command with include paths

**Warning signs:** User reports "VSCode can't find vendored library headers" or "autocomplete doesn't work for external dependencies."

**From research:** "If no command is available for a header, but a file has been opened that transitively includes it, then that file's command will be used." (clangd documentation) This is clangd's fallback, but explicit dependency commands are more reliable.

### Pitfall 2: Platform Path Separators in Ninja Files

**What goes wrong:** Build.ninja uses `\` on Windows, breaks when moved to Linux or when Ninja interprets `\` as escape character.

**Why it happens:** Go's `filepath.Join` uses OS-specific separators, but Ninja expects `/` on all platforms.

**How to avoid:** Always normalize paths to forward slashes in generated files:
```go
func ninjaPath(path string) string {
    // Ninja uses forward slashes on all platforms
    return filepath.ToSlash(filepath.Clean(path))
}
```

**Warning signs:** Build.ninja works on Windows but fails on Linux with "no rule to build target" errors.

### Pitfall 3: Incorrect `install_name` for macOS Dylibs

**What goes wrong:** Executable can't find shared library at runtime, fails with "dyld: Library not loaded" even when file exists.

**Why it happens:** macOS dylibs embed their install path in the binary. Default is absolute path to build location, which breaks when executable runs from different directory.

**How to avoid:** Set `install_name` to `@rpath/libname.dylib` during link:
```go
if platform == PlatformDarwin && targetType == "shared_library" {
    linkFlags = append(linkFlags, "-install_name", "@rpath/"+filepath.Base(output))
}
```

Then set `rpath` in executables that link the library:
```go
linkFlags = append(linkFlags, "-Wl,-rpath,@executable_path/../lib")
```

**Warning signs:** `otool -L myapp` shows absolute paths to `.dylib` files instead of `@rpath/` paths.

**Context decision:** Phase 7 context specifies `@rpath`-based approach for macOS (Claude's discretion).

### Pitfall 4: Symbol Visibility in Shared Libraries

**What goes wrong:** Shared library exports all symbols (huge binary, slow linking) or has symbol conflicts when multiple libraries define same symbol.

**Why it happens:** Default visibility is `default` (export everything). Large C++ projects expose thousands of symbols unnecessarily.

**How to avoid:**
1. Compile with `-fvisibility=hidden` by default for shared libraries
2. Add export macro for public API: `__attribute__((visibility("default")))`
3. Make it configurable per-target in CUE schema

**CUE config addition:**
```cue
#Target: {
    // ...
    symbolVisibility?: "default" | "hidden" // For shared libraries
}
```

**Warning signs:** `nm -gU libfoo.so | wc -l` shows thousands of symbols when API is small.

**Context decision:** "Symbol visibility: Configurable per-target in CUE config" (from 07-CONTEXT.md).

### Pitfall 5: Forgetting `-fPIC` for Shared Library Object Files

**What goes wrong:** Linker fails with "relocation R_X86_64_32 against `.rodata' can not be used when making a shared object."

**Why it happens:** Shared libraries require position-independent code. Object files compiled without `-fPIC` have absolute addresses.

**How to avoid:** Automatically add `-fPIC` when compiling sources for `shared_library` targets:
```go
func (c *Compiler) CompileFlags(target *config.Target, variant *config.Variant) []string {
    flags := []string{}

    if target.Type == "shared_library" {
        flags = append(flags, "-fPIC")
    }

    // ... rest of flag construction
    return flags
}
```

**Warning signs:** Build fails during link step with relocation errors (Linux/GCC) or builds but crashes at runtime (undefined behavior).

**Context decision:** "Position Independent Code (-fPIC) handling for shared libraries" is Claude's discretion—automatic is the correct choice.

### Pitfall 6: Ninja Rebuild Detection False Positives

**What goes wrong:** Ninja warns "build.ninja file changed during build" or reruns configuration unnecessarily.

**Why it happens:** Ninja checks if build.ninja is newer than last build. If generator writes file during build, Ninja detects staleness.

**How to avoid:**
1. Only write build.ninja when content actually changes (compare checksums)
2. Print warning if clue.cue is newer than build.ninja (per context decision)
3. Don't auto-regenerate during build (breaks Ninja's assumptions)

**Implementation:**
```go
func WriteIfChanged(path string, content []byte) (bool, error) {
    existing, err := os.ReadFile(path)
    if err == nil && bytes.Equal(existing, content) {
        return false, nil // No change
    }
    return true, os.WriteFile(path, content, 0644)
}
```

**Context decision:** "Stale config detection: Ninja prints warning if clue.cue is newer, but continues build (no auto-regeneration)."

### Ninja File Generation (Complete Example)

```go
// Source: github.com/Duncaen/go-ninja + Ninja manual
package generate

import (
    "io"
    "os"
    "path/filepath"

    "github.com/Duncaen/go-ninja"
    "github.com/loov/clue/internal/config"
)

func GenerateNinja(cfg *config.Config, variant string, outputPath string) error {
    file := ninja.File{}

    // 1. Set builddir for Ninja metadata
    file = append(file, ninja.Var{Key: "builddir", Val: ".ninja_build"})

    // 2. Define toolchain variables
    file = append(file, ninja.Var{Key: "cc", Val: cfg.Toolchain.Compiler})
    file = append(file, ninja.Var{Key: "cxx", Val: cfg.Toolchain.Compiler + "++"})

    // 3. Define compilation rule
    ccRule := ninja.Rule{
        Name:        "cc",
        Command:     "$cc -MD -MF $out.d $cflags -c $in -o $out",
        Depfile:     "$out.d",
        Deps:        ninja.DepsGCC,
        Description: "CC $out",
    }
    file = append(file, ccRule)

    // 4. Define link rules
    linkRule := ninja.Rule{
        Name:        "link",
        Command:     "$cxx $in -o $out $ldflags",
        Description: "LINK $out",
    }
    file = append(file, linkRule)

    // 5. Generate build statements for each target
    for _, target := range cfg.Targets {
        objects := []string{}

        for _, src := range target.Sources {
            objPath := ninjaPath(objectPath(cfg.BuildDir, variant, target.Name, src))
            srcPath := ninjaPath(src)

            build := ninja.Build{
                Rule: "cc",
                In:   []string{srcPath},
                Out:  []string{objPath},
                Vars: ninja.Vars{
                    {Key: "cflags", Val: buildCFlags(cfg, target, variant)},
                },
            }
            file = append(file, build)
            objects = append(objects, objPath)
        }

        // Link step
        outputPath := ninjaPath(outputPath(cfg.BuildDir, variant, target.Name, target.Type))
        linkBuild := ninja.Build{
            Rule: "link",
            In:   objects,
            Out:  []string{outputPath},
            Vars: ninja.Vars{
                {Key: "ldflags", Val: buildLDFlags(cfg, target, variant)},
            },
        }
        file = append(file, linkBuild)
    }

    // 6. Create phony targets for variants
    file = append(file, ninja.Build{
        Rule: "phony",
        In:   []string{ninjaPath(mainOutput)},
        Out:  []string{variant},
    })

    // 7. Write to file
    f, err := os.Create(outputPath)
    if err != nil {
        return err
    }
    defer f.Close()

    _, err = file.WriteTo(f)
    return err
}

func ninjaPath(path string) string {
    // Ninja uses forward slashes on all platforms
    return filepath.ToSlash(filepath.Clean(path))
}
```

### compile_commands.json Generation

```go
// Source: Clang JSON Compilation Database Format Specification
package generate

import (
    "encoding/json"
    "os"
    "path/filepath"

    "github.com/loov/clue/internal/config"
)

type CompileCommand struct {
    Directory string   `json:"directory"`
    File      string   `json:"file"`
    Arguments []string `json:"arguments"`
    Output    string   `json:"output,omitempty"`
}

func GenerateCompileCommands(cfg *config.Config, variant string, outputPath string) error {
    workDir, err := filepath.Abs(".")
    if err != nil {
        return err
    }

    commands := []CompileCommand{}

    // Add commands for all project targets
    for _, target := range cfg.Targets {
        for _, src := range target.Sources {
            srcAbs, _ := filepath.Abs(src)
            objAbs, _ := filepath.Abs(objectPath(cfg.BuildDir, variant, target.Name, src))

            cmd := CompileCommand{
                Directory: workDir,
                File:      srcAbs,
                Arguments: buildCompilerCommand(cfg, target, variant, src, objAbs),
                Output:    objAbs,
            }
            commands = append(commands, cmd)
        }
    }

    // Add commands for all dependency targets (for IDE navigation)
    for _, dep := range cfg.Dependencies {
        if dep.Build != nil {
            for _, src := range dep.Build.Sources {
                srcAbs, _ := filepath.Abs(filepath.Join(depPath(dep.Name), src))
                objAbs, _ := filepath.Abs(depObjectPath(dep.Name, src))

                cmd := CompileCommand{
                    Directory: workDir,
                    File:      srcAbs,
                    Arguments: buildDepCompilerCommand(cfg, dep, src, objAbs),
                    Output:    objAbs,
                }
                commands = append(commands, cmd)
            }
        }
    }

    // Write JSON
    data, err := json.MarshalIndent(commands, "", "  ")
    if err != nil {
        return err
    }

    return os.WriteFile(outputPath, data, 0644)
}

func buildCompilerCommand(cfg *config.Config, target *config.Target, variant string, src, obj string) []string {
    // CRITICAL: Reuse internal/build package logic, don't reimplement
    // This ensures compile_commands.json matches actual build exactly
    args := []string{cfg.Toolchain.Compiler}
    args = append(args, "-c")
    args = append(args, src)
    args = append(args, "-o")
    args = append(args, obj)

    // Add all flags (reuse build package)
    args = append(args, compilerFlags(cfg, target, variant)...)

    return args
}
```

### Shared Library Platform-Specific Handling

```go
// Source: Research on macOS install_name and Linux -fPIC
package generate

func buildLinkFlags(cfg *config.Config, target *config.Target, platform Platform) []string {
    flags := []string{}

    if target.Type == "shared_library" {
        // All platforms: create shared library
        if platform == PlatformLinux || platform == PlatformDarwin {
            flags = append(flags, "-shared")
        }

        // macOS-specific: set install_name with @rpath
        if platform == PlatformDarwin {
            libName := "lib" + target.Name + ".dylib"
            flags = append(flags, "-install_name", "@rpath/"+libName)
        }

        // Linux-specific: set soname (simple version, no versioning per context)
        if platform == PlatformLinux {
            libName := "lib" + target.Name + ".so"
            flags = append(flags, "-Wl,-soname,"+libName)
        }
    }

    // Add rpath for executables that depend on shared libraries
    if target.Type == "executable" && hasSharedLibDeps(cfg, target) {
        if platform == PlatformDarwin {
            // Look for libs relative to executable
            flags = append(flags, "-Wl,-rpath,@executable_path/../lib")
        } else if platform == PlatformLinux {
            // $ORIGIN is Linux equivalent of @executable_path
            flags = append(flags, "-Wl,-rpath,$ORIGIN/../lib")
        }
    }

    return flags
}

func buildCompileFlags(cfg *config.Config, target *config.Target) []string {
    flags := []string{}

    // Automatically add -fPIC for shared libraries
    if target.Type == "shared_library" {
        flags = append(flags, "-fPIC")
    }

    // Symbol visibility (configurable)
    if target.Type == "shared_library" && target.SymbolVisibility == "hidden" {
        flags = append(flags, "-fvisibility=hidden")
    }

    return flags
}
```

## Open Questions

1. **Integration with existing build package**
   - What we know: internal/build has Compiler, Linker, Builder with full command construction logic
   - What's unclear: Should generators call Builder.Build() to get commands, or duplicate logic?
   - Recommendation: Create new `internal/build.CommandBuilder` interface that both Builder (for direct build) and generators (for file generation) can use. Avoids duplication, ensures consistency.

2. **Variant selection for compile_commands.json**
   - What we know: Context says "default variant: debug" for compile_commands.json
   - What's unclear: Should `clue generate compile-commands -variant=release` be supported?
   - Recommendation: Support variant flag, default to debug. IDE users may want release for performance testing.

3. **Dependency build commands in compile_commands.json**
   - What we know: Users need to navigate into dependency headers
   - What's unclear: Should we include external git/tarball dependency sources in compile_commands.json?
   - Recommendation: YES—include all dependency sources. This is critical for IDE navigation. Context says "Include dependencies: Yes, all dependency sources included."
